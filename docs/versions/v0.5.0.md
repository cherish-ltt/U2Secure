# v0.5.0 — SSH 安全边界、批次恢复与隔离测试

> 文档日期：2026-11-02
>
> 本文记录版本变更与发布前验证，不代表 GitHub Release、npm 或 crates.io 已发布成功。
> 发布状态需以对应工作流、资产及注册表记录为准。

本版本修复 SSH 密钥文件操作、批次撤销、SSH 生效与防火墙协同、长命令取消及发布链路问题，
并在全部原修复 PR 合并后，通过独立测试 PR 将全项目行覆盖率提升至 **85.50%**。
仅支持 Linux x86_64 与 ARM64；macOS 只用于受隔离保护的编译和测试。

## 一、SSH 密钥安全与升级前检查

本版本包含 [GHSA-qfch-m8ff-xfvx](https://github.com/cherish-ltt/U2Secure/security/advisories/GHSA-qfch-m8ff-xfvx)
对应的 SSH 密钥路径安全修复。

- 从账户数据库解析目标账户的 home、UID 与 GID，逐级打开并验证目录，不跟随目录符号链接。
- home 与 `.ssh` 必须归目标账户所有，且不得允许组或其他用户写入；祖先目录也接受归属和可写性检查。
- `authorized_keys` 只接受经文件描述符验证的普通单硬链接文件；已有文件必须归目标账户所有。
  写入和权限设置作用于已验证的文件描述符，不再对不可信路径直接执行 root 权限的修改。
- `.ssh` 缺失时只以目标账户身份创建，再重新验证；账户初始化不再通过路径式权限命令绕过同一边界。
- 密钥对生成复用目录检查，在私有临时目录执行生成，再写入已验证的目标文件。

**兼容性变化**：以前可能被接受的符号链接 home、`.ssh`、`authorized_keys`，
硬链接或非常规密钥文件，以及归属或目录权限不安全的布局，现在会明确拒绝。
升级前应由管理员核对账户数据库与真实目录布局，保留必要备份，并在隔离环境验证调整；
不要通过忽略错误或对用户可控路径递归修改归属来绕过检查。

密钥替换与恢复同时调整：

- `GenerateNew` 遇到已有密钥不再隐式覆盖；必须明确选择 `ReplaceExisting`。
- 替换前保留原字节与权限，批次撤销时恢复；恢复失败保留备份并报告位置，不假装成功。
- 撤销不会盲目删除已被替换成另一文件的路径；路径变化作为恢复错误报告。
- 同批次为新用户生成过密钥后，重复的同用户 `GenerateNew` 会明确跳过。
- 成功批次或 SSH 生效边界提交后会释放临时密钥备份；它不是长期备份或灾难恢复机制。

## 二、SSH 配置与运行时生效分开处理

SSH 审计以 `sshd -T` 的有效全局配置为依据，修改时先对候选配置执行语法与有效值验证，
避免将没有真正生效的文本修改报告为加固成功。
存在 `Include`、`Match` 或多个监听端口时，报告保留“未完全验证”状态；
未提供连接上下文的 `sshd -T` 不能证明所有 `Match` 分支安全。

选择 SSH 配置步骤后，共用执行器会将生效检查排到批次末尾：

- CLI/TUI 在执行前收集是否应用 SSH 配置的明确授权；无授权不重启，报告待生效。
- 只有本批实际写入或已有待生效配置时才需要重启；单纯重复检查不触发重启。
- 若 SSH 仍待生效且 UFW 原本关闭，暂不启用 UFW，避免仅放行新端口却切断仍监听旧端口的服务。
  确认 SSH 生效和新连接可用后，再执行防火墙步骤。
- 服务选择先检查 systemd 的 `LoadState`；只有 `sshd` 明确不存在才改用 `ssh`，
  不以另一个服务名掩盖已有服务的重启失败。

### 重要：开始尝试重启是整批提交边界

| 发生阶段 | 失败或中断后的行为 |
|----------|------------------|
| 语法验证、服务发现或重启前 | 按批次撤销已登记的操作，并报告恢复错误 |
| 即将执行 `systemctl restart` 起 | 提交本批撤销记录，保留用户、密钥、配置和防火墙变更 |
| 重启或后续状态查询失败、超时、中断 | 明确报告失败、修改保留及需要人工检查，不自动只回滚文件或规则 |

这一边界防止服务可能已切换到新端口后，仅恢复旧防火墙规则造成新的失联。
它**不能保证服务启动成功或远程连接可用**。
管理员应保留现有 SSH 会话，并准备控制台或带外访问；不要在验证新连接前关闭唯一管理会话。

## 三、其他可观察修复

| 场景 | 修改前 | 修改后 |
|------|--------|--------|
| 成功执行一批后，下一批失败 | 旧撤销记录可能影响已成功批次 | 成功批次提交撤销记录，只恢复当前批次 |
| 新用户初始化中途失败 | `useradd` 成功后的部分初始化可能缺少撤销记录 | 创建成功即登记撤销，后续错误可触发恢复 |
| 同一文件短时间多次备份 | 时间命名可能碰撞并覆盖旧备份 | 每次备份使用唯一文件 |
| 恢复命令或文件恢复失败 | 错误可能被吞掉，唯一备份可能丢失 | 汇总恢复错误并继续独立撤销；恢复失败保留备份 |
| SSH 改端口与 UFW 规则修改 | 放行错误可能未阻止后续写配置，撤销可能删除既有规则 | 放行失败阻止后续写配置；保存规则文件和原启用状态供恢复 |
| 审计 `Status: inactive` | 子串匹配把 inactive 当成 active | 固定英文输出，要求命令成功并精确识别 active |
| 长命令超时、无输出或取消 | 只终止直接子进程，后台任务可能继续 | 终止所管理的进程组；Linux 在主进程正常退出后也清理同组后台任务 |
| APT 索引部分下载失败 | 退出成功可能掩盖镜像错误 | `APT::Update::Error-Mode=any` 将索引错误交给失败处理；预热最多尝试 3 次再由用户决策 |
| TUI 探测任务断连 | 探测可能消费尚未呈现的业务事件 | 由 `drain()` 统一消费事件，断连查询只读取状态 |
| npm 二进制下载中断或写入失败 | 残缺产物可能覆盖已有文件或被当成成功 | 临时文件完整性检查通过后再替换；失败非零退出并保留原文件 |
| 从 `main` 手动构建指定标签 | 下游可能把 `head_branch=main` 当版本标签 | 从同一个 Binary Build run 的 `release-tag` artifact 读取标签 |

UFW 快照范围为 `user.rules`、`user6.rules`、`ufw.conf` 及启用状态，不是整个系统防火墙状态的快照。
进程组清理不涵盖主动脱离该组的守护进程，也不保证立刻终止不可中断的内核 I/O。
这些修复不使所有加固操作成为完全可逆事务；可选步骤失败仍按原约定记录并继续，
软件包操作的外部副作用也不保证完整撤销。

## 四、Rust 调用方迁移

本版本存在公开 API 兼容性变化。直接依赖库接口的调用方应重新编译并检查以下项目：

| 接口 | 变化与迁移要求 |
|------|----------------|
| `AuditReport` | 新增 `ssh_config_verified`；不能只看单个 SSH 布尔值就认定所有上下文已验证 |
| `ExecuteParams` | 新增 `apply_ssh_changes`、`ssh_restart_required`，默认均为 `false`；结构体字面量可使用 `..Default::default()` 补齐默认值，但应用 SSH 必须显式授权 |
| `StepResult` | 新增 `ssh_restart_required`、`ssh_activation_attempted`；优先使用 `changed`、`skipped`、`failed` 等构造器 |
| `SshKeyAction` | 新增 `ReplaceExisting`；穷尽匹配需补分支，不能把普通生成视为覆盖授权 |
| `UndoAction` | `execute()` 改为 `Result<(), DomainError>`；兼容保留 `new()`，可能失败的撤销应使用 `try_new()` |
| `rollback::undo_all()` | 返回 `Vec<String>` 汇总恢复错误，调用方必须呈现错误而不是直接宣称恢复成功 |
| `system` SSH 检测函数 | 删除 `sshd_config_get`、`detect_password_auth_disabled`、`detect_root_login_disabled`；改用 `SshConfig::effective()` 并检查 `verified`，或 `run_full_audit()` |
| `JobHandle` | 先调用 `drain()` 再判断 `is_disconnected()`；后者不再主动消费事件，`JobEvent::Interrupted` 不表示已全部回滚 |

自定义 `HardeningStep` 修改 SSH 配置后，应通过 `requiring_ssh_restart()` 报告实际写入；
尝试应用服务配置后，成功和失败结果都必须正确携带 `ssh_activation_attempted`，避免丢失提交边界。
`StepRunner::run` / `spawn` 会自动补齐 SSH 生效计划，
`run_steps` / `spawn_steps` 仍执行调用方提供的计划，自定义调用方需自行使用 `execution_plan`。

## 五、发布前验证与限制

全部原修复 PR 合并后，再合并独立覆盖率 PR [#34](https://github.com/cherish-ltt/U2Secure/pull/34)。
以下记录针对版本准备前的集成代码，合并基底为 `8880dd11cb11a2d98c811a50fea950af7cb6dd63`：

| 验证项 | 实际结果 |
|--------|----------|
| `cargo llvm-cov --locked --all-targets --all-features --summary-only` | 全项目行覆盖率 **85.50%（6117 / 7154）**；未通过额外排除文件缩减口径，无覆盖率警告 |
| 同次全量 Rust 测试 | **195 passed / 0 failed / 0 ignored** |
| `prek run --all-files` | 所有适用 hook 通过；JSON 检查因无匹配文件跳过 |
| `cargo build --locked` | 通过 |
| `cargo check --locked --target x86_64-unknown-linux-gnu` | 通过；这是交叉编译检查，不是目标机运行验收 |
| npm 安装器独立测试 | 12 个场景通过，覆盖完整下载、截断、请求错误、HTTP 错误、写入失败和长度不匹配 |
| 发布标签工作流 fixture | 2 项通过 |

`prek` 曾提示旧 Node hook 缓存版本不匹配，但随后所有适用 hook 均实际执行通过，
没有以该警告为由跳过适用检查。SSH 配置与密钥生命周期测试的全局撤销栈竞争
已通过独立子进程隔离，并完成重测。

测试采用临时目录、私有 PATH 假命令、注入配置与内存终端；macOS 上额外禁止联网和系统目录写入。
没有运行真实 CLI/TUI 加固入口，也没有为提高覆盖率修改宿主系统。
`main.rs`、CLI 交互及真实系统集成仍有未覆盖部分；85.50% 不代表每个模块均达到 80%，
也不构成真实 Linux 加固、远程 SSH 连通性或独立安全审计的验收证明。

## 六、发布顺序与已知限制

1. 版本文件与标签一致后，推送 `v0.5.0` 触发 Binary Build，构建两个 Linux 目标。
2. 确认整个 Binary Build 成功，GitHub Release 同时具有
   `u2secure-x86_64-unknown-linux-gnu` 和 `u2secure-aarch64-unknown-linux-gnu`。
3. npm 的 `workflow_run` 自动路径在上游成功后发布，从触发 run 的 `release-tag` 读取版本；
   同版本已存在则跳过发布。
4. **crates.io Trusted Publishing 不接受 `workflow_run`**，需要在确认二进制就绪后使用
   `cargo-publish.yml` 的 `workflow_dispatch`，传入 `tag_name=v0.5.0`。
   不能把自动工作流已触发视为 crate 已发布。
5. 最后分别核对实际发布运行、Release 资产、npm 与 crates.io 的版本元数据。
   手动入口本身不替维护者验证 Binary Build 成功；crates.io 也没有同版本重复发布的幂等跳过。

Trusted Publishing 限制见 [Rust 官方说明](https://blog.rust-lang.org/2026/01/21/crates-io-development-update/)，
历史错误记录已在 [v0.4.1 发布说明](v0.4.1.md) 中更正。
不要在 macOS 直接运行程序来查询版本；当前入口不支持 `--version`，且会在解析参数前初始化日志器。
