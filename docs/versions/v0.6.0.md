> 文档日期：2026-11-05
>

本版本实现 [Issue #36](https://github.com/cherish-ltt/U2Secure/issues/36)：
以独立命令输出本机审计报告，支持文本和稳定 JSON，无需进入交互式加固流程。
发布矩阵包含 Linux x86_64、ARM64 的 GNU 与 musl 共四个目标；macOS 仅用于隔离编译和测试。

## 一、只读审计命令

```bash
sudo u2secure audit                    # 默认文本报告
sudo u2secure audit --format json      # 单个 JSON 文档
u2secure audit --help                  # 查看用法，不采集系统状态

# 保存由调用方负责；已有文件的权限需另行检查。
(umask 077; sudo u2secure audit --format json > audit.json)
```

- 参数在采集前校验；审计要求 root，可在管道、关闭 stdin 或无 TTY 的环境运行。
- 不进入语言选择、CLI/TUI、加固执行器或日志初始化，不自动创建日志、报告、备份或扫描产物。
- stdout 只输出报告，失败诊断写入 stderr。文本具备简体中文、英文与繁体中文翻译，独立命令使用默认简体中文。
- 每条外部探测限时 5 秒，stdout 与 stderr 合计最多 1 MiB，在内存中采集；正常结束、失败、超时、超限或取消时清理同一进程组并回收直接子进程。

退出码 `0` 只表示报告输出成功或帮助已显示，不代表系统已安全。
工具未安装、功能未配置与 SSH 未验证均可作为正常发现返回。
参数错误、权限不足、必要探测失败、超时、超限、配置读取错误及 stdout 写入或刷新失败返回 `1`。
采集或序列化失败不输出半份报告；输出设备中途失败时，调用方应丢弃已收到的内容并检查退出码。

### JSON schema 1

顶层字段为 `schema_version`、`tool_version`、`collected_at`、`check_scope`、`is_root`、
`package_manager`、`checks`。`checks` 固定涵盖全部 12 个加固步骤，使用现有步骤 slug 作为 ID，
状态仅取 `safe`、`partial`、`missing`、`needs_update`，与交互式界面共用 `AuditReport::status_for()`。

`details` 仅提供最小类型化结果，不包含原始命令输出、配置正文、密钥或本地化审计文案。
未验证的 SSH 端口和认证设置使用 `null`，不会用默认值伪装成已知结果。
JSON 的字段、ID、状态、范围代码及详情不随界面语言变化；完整契约见 README 的“只读审计报告”。

## 二、检查范围与失败边界

| 检查 | 本版本明确的边界 |
|------|------------------|
| SSH | 仅 `sshd -T -f` 的全局配置；Include、Match、多端口或无法取得有效配置时保持未验证。不验证真实连接或密钥，也不保证远程登录可用 |
| UFW | 使用只读 `iptables-save -M /bin/false`，按配置需要查询 IPv6；只检查 filter 表的三条 UFW 用户链，不验证完整规则或并发重载时的原子一致快照 |
| 系统更新 | 仅按 APT 缓存是否小于 7 天判断，不查询待升级包或证明软件包已升级 |
| 管理用户 | 仅检查 sudo/wheel 管理组成员，不解析完整 sudo 策略 |
| 安全扫描与日志工具 | 只检查 Lynis、Logwatch、AIDE 是否安装，不运行扫描，不验证数据库或历史报告 |
| SSH 待重启 | 仅比较配置与进程时间戳；未提示重启不证明运行配置已生效 |

UFW 审计不执行会创建 `/run/ufw.lock` 的 `ufw status`，也不指定 `iptables-save` 的
`-t` / `-f` 参数，不主动指定未加载的表或写入文件。`-M /bin/false` 禁止用户态模块加载；
不保证内核在并发卸载等竞态下绝不自动加载模块。
SSH 配置不存在或 `sshd` 不存在、普通非零退出可以报告未验证；配置不可读取、不是普通文件、
超出读取限制或不是 UTF-8 则明确失败，不伪装成正常发现。

审计报告包含管理用户名与安全配置状态，保存或分享前应检查权限。
命令限制针对单条探测，整份审计没有固定总耗时上限；主动脱离进程组的守护进程不在清理保证内。

## 三、交互式审计与 Rust 调用方

独立命令、CLI 与 TUI 共用同一采集与状态判断，采集失败通过 `Result` 显式传播。
CLI 审计失败以非零退出；TUI 初始审计在终端进入 raw mode 前执行，刷新失败保留旧报告并显示错误。
取消加固批次后，下一次显式审计重置该次入口的中断状态，避免旧取消状态使新审计立即失败。

直接依赖库接口的调用方需要适配以下返回类型变化：

| 接口 | 迁移 |
|------|------|
| `system::run_full_audit()` | 返回 `Result<AuditReport, DomainError>`，调用方必须处理采集错误 |
| `HardeningOrchestrator::audit()` | 同样返回 `Result`；只有成功采集才写完成日志 |

## 五、Linux 资产与发布顺序

本版本的发布矩阵为：

| 架构与链接目标 | Release 资产名 |
|----------------|----------------|
| Linux x86_64 GNU | `u2secure-x86_64-unknown-linux-gnu` |
| Linux ARM64 GNU | `u2secure-aarch64-unknown-linux-gnu` |
| Linux x86_64 musl | `u2secure-x86_64-unknown-linux-musl` |
| Linux ARM64 musl | `u2secure-aarch64-unknown-linux-musl` |

musl 扩展二进制链接目标，不扩大受支持的加固发行版范围；npm 安装器继续选择 GNU 资产。
musl 由对应架构的 Linux runner 配合 `musl-tools` / `musl-gcc` 构建，不发布 macOS 或 Windows 二进制。

版本文件与标签一致后推送 `v0.6.0`，等待 Binary Build 全部成功并核对四个资产齐全。
npm 随成功构建自动发布；crates.io 仍需在确认资产就绪后以 `cargo-publish.yml` 的
`workflow_dispatch` 传入 `tag_name=v0.6.0`，因为 crates.io Trusted Publishing 不接受 `workflow_run`。
最后核对 Release、npm 与 crates.io 的实际版本元数据，不能仅以标签或工作流触发作为发布完成依据。
