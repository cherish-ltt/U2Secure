# v0.4.1 — AIDE 初始化修复与发布流水线顺序修正

> 发布时间：2026-09-27

本版本修复步骤 11（日志与审计增强）中 **AIDE 数据库初始化必然失败** 的缺陷，
并将 npm / crates.io 发布改为在二进制构建成功之后执行。

---

## 一、AIDE 数据库初始化失败（步骤 11）

### 现象

安全扫描结果显示"日志与审计增强失败"，子项为
`aide 数据库初始化失败（退出码 17）`，手工执行报错：

```
ERROR: missing configuration (use '--config' '--before' or '--after' command line parameter)
```

### 根因（已核实）

1. **发行版把配置拆成了两个包**。以 Debian/Ubuntu 为例，`aide` 包的安装清单
   只有 `usr/bin/aide` 与两个 man page，而配置文件 `aide.conf` 与 `aideinit`
   脚本由 **`aide-common`** 提供（`/etc/aide/aide.conf`、`/usr/sbin/aideinit`）。
   只装 `aide` 的系统上不存在任何 aide 配置。
2. **AIDE 退出码 17 的确切含义是 Configuration error**（见 `aide(1)` 的
   EXIT STATUS 一节，`include/errorcodes.h` 中 `INVALID_CONFIGURELINE_ERROR 17`），
   即"找不到或无法解析配置"，与"扫描发现异常"无关。
3. **旧实现直接执行裸命令** `aide --init`（无 `--config`，且无配置兜底逻辑），
   在上面的系统上必然以 17 退出，且失败只记录一行原因，未指出配置缺失。

### 修复内容

新增 `src/infrastructure/aide.rs` 负责配置发现与初始化编排，步骤 11 不再自己拼命令：

| 环节 | 修复后行为 |
|------|-----------|
| 安装 | Debian/Ubuntu 追加安装配置包 `aide-common`（通过 `package_mirror::install_argv` 走临时源）；软件包是否已装改用 `dpkg-query` / `rpm` 判断，因为 `aide-common` 没有可执行文件，`which` 无法识别 |
| 配置发现 | `aideinit`/`aide.wrapper` 的 `CONFIG=` → `/etc/aide/aide.conf`（apt）→ `/etc/aide.conf`（rpm），并读取其中 `database_in` / `database_out`，不写死 `/var/lib/aide` |
| 配置校验 | 用 `aide --config-check` **只读校验**语法；缺失或不可用时才生成兜底配置 |
| 兜底配置 | 生成到报告目录（`/var/log/u2secure/aide-u2secure.conf`），**只使用各版本通用配置项**，不依赖发行版 `aide.conf.d`；数据库使用独立文件名 `aide-u2secure.db`，**不会覆盖系统既有基线**；若目标路径已有非本工具生成的文件，改写入带时间戳的新文件，绝不覆盖用户配置 |
| 初始化 | 优先 `aideinit -y -f -c <conf>`（自动处理 `_aide` 用户与 `/var/log/aide` 日志），无 `aideinit` 时用 `aide --config=<conf> --init` |
| 数据库落地 | 初始化后把 `database_out` 复制为 `database_in`（含 `.gz` 变体识别），并将权限收紧到 0600 |
| 可用性验证 | 初始化成功**不等于**可用，随后立即执行 `aide --check` 验证；退出码 1–7 是"发现文件差异"的正常结果，≥14 才判定失败 |
| 每日检查 | 脚本显式带上本次实际生效的 `--config`，避免再次踩"缺配置"；退出码 ≥14 才报错，1–7 视为正常差异；已存在 `dailyaidecheck`（Debian）或 `dailyaidecheck.timer` 时不重复添加 |
| 失败处理 | 保留原始错误、退出码与日志路径，不伪造成成功；步骤仍按可选步骤语义**只记录失败、不触发全局回滚** |

### 结果摘要新增内容

步骤 11 的完成消息现在会给出：

```
  aide 配置文件: /etc/aide/aide.conf
  aide 数据库: /var/lib/aide/aide.db (mode=600)
  aide 初始化日志: /var/log/u2secure/aide-init-<时间戳>.log
```

## 二、发布流水线：包发布跟在二进制构建成功之后

`npm-publish-manual.yml` 与 `cargo-publish.yml` 不再监听 `push: tags: v*`，
改为"等二进制就绪后再发包"。两者触发器不同（原因见下）：

| 工作流 | 触发器 | 等待方式 | 标签来源 |
|--------|--------|---------|---------|
| npm | `workflow_run`（`Binary Build` 完成） | job 级 `if` 判断 `conclusion == 'success'` | `workflow_run.head_branch` |
| crates.io | `workflow_run`（同上） | 额外用 `gh api` 轮询等 `Binary Build` 到 success 终态 | `workflow_run.head_branch` |

- 消除"npm 版本号已上线、GitHub Release 二进制仍 404"导致 `postinstall` 安装失败的窗口
- **crates.io 不能使用 `release: [published]`**：Release 由
  `softprops/action-gh-release` 用 GITHUB_TOKEN 创建，GitHub 规定 GITHUB_TOKEN
  触发的事件不会创建新的 workflow run（仅 `workflow_dispatch` / `repository_dispatch`
  例外），实测发布 Release 后没有任何 release 事件的运行记录，crates.io 会永不发布
- crates.io 的 Trusted Publishing 允许 `workflow_run`（实测通过鉴权）；它拒绝的是
  "由 workflow_run 触发的不可信代码"使用 OIDC token，本工作流运行在默认分支的可信代码上
- 两个工作流的差异只在等待方式：npm 用 job 级 `if`，crates.io 用 `gh api` 轮询
  （job 排队期间 `conclusion` 可能为空，只靠 `if` 不可靠）
- 标签解析失败立即报错而不是误发；`cargo-publish` 额外校验 `Cargo.toml` 版本与标签一致
- 两者都保留 `workflow_dispatch` 作为应急手动补发入口
- npm 增加幂等保护：同版本已存在则跳过发布，重跑安全

**v0.4.1 是该流程的首次实际验证**：预期 npm / crates.io 的启动时间晚于
Binary Build 完成时间。

首次推送 v0.4.1 标签时，Binary Build 的 Windows 目标编译失败，而 npm 与 crates.io
被门禁**正确跳过**（`skipped`），没有出现"二进制没成功、包却先发出去"的情况——
这正是本次改造要保证的语义。

## 三、构建目标收敛为 Linux

U2Secure 依赖 apt/dnf、ufw、sshd、systemd、`/var/log`、`/etc` 等 Linux 专有组件，
`--check` 类逻辑（如 `/proc/<pid>` 时间戳比较）也只在 Linux 上成立。
此前工作流仍构建 macOS 与 Windows 产物，属于"能编译但不可用"，现予移除：

- `binary-build.yml` 构建矩阵只保留 `x86_64-unknown-linux-gnu` 与
  `aarch64-unknown-linux-gnu`，不再申请 macOS/Windows runner
- npm 包 `postinstall` 在非 Linux 平台直接给出明确报错，
  不再尝试下载一个永不存在的资产
- `src/main.rs` 增加 `#[cfg(windows)] compile_error!`，避免误产出 Windows 二进制；
  macOS 仍可编译，便于在开发机上运行单元测试
- 顺带修复由此暴露的真实缺陷：步骤 11 写 cron 脚本时用
  `std::os::unix::fs::PermissionsExt` 设置可执行位，该模块在非 unix 目标不存在；
  现已收敛到带 `#[cfg]` 的 `set_executable()` 辅助函数

| 验证项 | 方式 | 结果 |

| `init` / `check` / `--config-check` 命令构造均显式带配置 | 单元测试 | 通过 |
| 退出码语义（1–7 为差异、17 为配置错误不误判） | 单元测试 | 通过 |
| 每日脚本容错（≥14 才失败、日志路径正确） | 单元测试 | 通过 |
| 包安装状态解析（dpkg 已卸载/未安装、rpm 未安装） | 单元测试 | 通过 |
| `cargo fmt` / `clippy -D warnings` / `cargo test`（96 项） | 本地 | 全部通过 |
| `prek run --all-files` | 本地 | 全部通过 |
| **真实 Linux 上 AIDE 的 `--init` / `--check` 行为** | **未验证** | 开发机为 macOS，无法执行 AIDE；需在目标 Linux 上实测 |

### 建议的人工验证步骤（Linux，root）

```bash
# 1) 修复前：确认缺陷（只装 aide 的环境）
aide --init; echo "退出码=$?"          # 预期 17 且报 missing configuration

# 2) 运行 U2Secure 并勾选步骤 11
sudo u2secure

# 3) 确认配置与数据库
grep -E '^database_(in|out)' /etc/aide/aide.conf    # 或报告目录里的 aide-u2secure.conf
ls -l /var/lib/aide/                                # 数据库存在且权限 600

# 4) 确认检查可用且不再报"缺少配置"
aide --config=/etc/aide/aide.conf --check; echo "退出码=$?"   # 预期 0 或 1-7

# 5) 确认每日检查
cat /etc/cron.daily/99u2secure-aide
```

## 五、升级说明

- 版本号：`0.4.0` → `0.4.1`（`Cargo.toml`，源码统一用 `env!("CARGO_PKG_VERSION")` 读取）
- 已初始化过 AIDE 的系统不会被重新初始化（检测到数据库即跳过）
- 数据库与配置的兜底路径均使用独立命名，不会覆盖系统既有内容
- **破坏性变更**：不再提供 macOS / Windows 预编译二进制。
  在上述平台通过 `npm install -g` 安装会得到明确的"仅支持 Linux"提示；
  请改用 Docker 或 Linux 服务器/虚拟机。Linux 功能不受影响。
